# 記録11：同じ履歴から再生する（3周目）

2026-11-22、方針の版11。11/21 06:15の返事に従い、本体接続はリーダーが持つ。Bは共通保存の入口・見本・試験まで。記録10は原値保持と注意表示までで確定、復元元の再確認は求めない。

## 保存の入口

`createRunStore()` は `RunRecord`・`StoredRunDetail`・`ReplayRecord`を同じIDの1件にまとめる。到達した天体も照合するため、同じ終了時点の `GameSnapshot`も渡す。共有文字列は再生から導出し、別の保存として重複させない。

ブラウザはIndexedDBの同じreadwrite transactionで最新データの読込・ID統合・保存を行う。画面側は表示するたびに `await store.ready()`、終了時の呼出しは `await store.add({ record, detail, replay, final })`。`ok:true`でも `persisted:false`なら、保存できたと表示せずページ内だけの保持と伝える。11/24の4周目では、通常のDB保存中のlocalStorageへの写しを止めた。open失敗時の切替と結果は [4周目](../records-cycle4/checks.md)を参照。

## 審査で直した★

1. 複数タブ：メモリだけの追加は別タブの記録を失った。Web Locksで直列化しても、直後のlocalStorageが前タブの書込を見ない回が20回中1回あった。待ち時間を足す対処は採らず、IndexedDBのtransactionへ変更した。新しいブラウザ保存領域で20回、2ページから同時に保存し、全40件が保存成功。新規の第3ページでも全20回で2件を保持した。
2. 復旧：壊れた主データで正常backupを使わず、次の保存で壊れた原文をbackupへ上書きした。正常backupを復旧候補にし、壊れた原文は別の退避へ残す。表示だけでは既存の主データ・backupを書き換えない。
3. 到達した天体：履歴と統計の到達値を両方改変すると、元の再生と違っても通った。終了盤面の指紋と到達値、得点・seed・tick・phase・統計・天体数を照合し、不一致を拒否する。

審査役の再確認で上の★は再現しなかった。これは動作・数値・保存の審査で、見た目の合格ではない。

## 保持と未確認

- 履歴は最大1000件、再生は新しい最大100件かつアーカイブ150万文字以内。元の旧キーとbackupを削除しない。IDの無い古い再生を、似た得点や日時の履歴へ推測で結び付けない。
- 特別な開始盤面・古いルールの再生は保持し、共有できない理由を表示する。個別の保存削除・取り消し、特殊開始の専用再生導線は次の改善候補。
- 本体終了処理へは未接続。人の実機操作、見た目の良し悪し、通常の自動作業が1回終了してpushすることは未確認。実予約からの診断応答と読み取り操作の成功は、これらと分けている。

仕様の根拠：[Indexed Database APIのtransaction scheduling](https://www.w3.org/TR/IndexedDB/#transaction-scheduling)。同じ保存対象のreadwrite transactionが重ならず、後続が先行の変更を見る性質を使う。外部ライブラリは追加していない。
