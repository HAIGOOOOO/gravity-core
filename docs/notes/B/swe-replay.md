# プレイの再生（swe-replay）

## いま
- 検証に上限を付けた: endTick が MAX_REPLAY_TICKS（1 時間 = 432,000 tick）を
  越える記録は、再計算を始める前に 'tooLong' を返す。終わらない盤面で
  endTick だけ書き換えた記録を渡されると、これまでは実質止まらなかった。
- カーソルが途中で盤面を書き戻す処理を整理: 間隔の倍数の盤面は検証で
  全部 keyframes に入っているので、advance/seek の再記憶は到達不能だった。
  「行った所」への記憶だけを残した。
- 見どころの量（連鎖数・超新星の回数・最高 Tier）と、記録の統計・
  最終盤面の突き合わせスイープを replay-cross.test.ts に追加。

## つぎ
- 30 分級の実長記録の計測は別枠（自動プレイ生成が重い）。cap で等価再現済み。
- 上限を越えた記録を「部分的にでも再生する」かは未決。いまは全部止める。
  （再生自体は同じコストが掛かるので、止めるのが素直と判断）

## 「tick T の盤面」の決め方（一番大事な約束）
`submitLaunch` は呼んだ時点の tick で盤面へ即反映される。元のプレイでは
「tick T の盤面」は T 回の stepFixed のあと・tick T の入力が撃たれる前に取られる。だから:
- 盤面 T = 「tick < T の入力」を反映して T 回進めた状態
- 入力 tick = T は盤面 T のあと、T→T+1 のステップの前に投入される
- 例外は記録の「最後」だけ: 記録直前に撃たれて 1 回も進んでいない入力（tick = endTick）が
  ありうるので、最終盤面の照合時だけ endTick の入力も反映する（再現側も同じ状態になる）
- この例外は endTick = 0 にも効く: 「盤面 0」= 開始盤面 + tick 0 の入力。
  だからプレイヤーの最初の盤面はキーフレーム（上書き済みの最終盤面）から取る。

## seek の速さの設計
SimulationPort の中身は外から複製・復元できない。ある tick の状態は
「シードと入力から計算し直す」しかないので、速さを 3 段に分ける（player.ts 冒頭に詳細）:
1. キーフレーム: 検証の再計算で一定間隔の盤面を覚える。捨てない。
   その tick への seek/peek は一瞬。長い記録では間隔を広げ、
   面数が KEYFRAME_CAP(720) 程度に収まるようにする（間隔は keyframeInterval()）。
2. 行った所: seek で止まった盤面も覚える。上限 240 面を越えたら一番古い物から捨てる
   （Map の挿入順を利用した LRU もどき）。同じ所への再 seek は一瞬で、
   peek もここを引く（止まった tick ちょうどの盤面がキーフレームより優先して出る）。
3. カーソル: 前にしか進めない sim を最大 4 本持ち、目的地の手前にいる物を進める。
   全部先にいる時は一番手前（最小 tick = 失う計算が最小）を捨てて 0 から作り直す。
   最悪は全計算し直し。カーソルが進めなくなる（終了した）異例に備え、
   盤面の tick は常に snapshot から取り、記憶のキーにも実際の tick を使う。
ツマミを動かしている途中の表示は peek（近いキーフレームを即返す）を使う想定。

## 検証の上限（tooLong）
「記録と合うか」の確かめは、endTick ぶん全部計算し直す仕組み上、
記録の長さに比例して掛かる。終わらない盤面（静かな記録）で endTick だけを
大きく書き換えた記録を渡されると、再計算が実質止まらない。
そこで endTick が MAX_REPLAY_TICKS（既定・1 時間ぶん）を越える記録は、
盤面を作る前に tooLong で止める。「合わない」(diverged) とは別の理由にした:
記録自体が正しい可能性が残る（本当に長いプレイかもしれない）ので区別し、
上限は options.maxTicks（player も同じ option）で変えられる。
判定の順は rulesVersion → tooLong → 盤面の照合（安い順）。

## 記録と合わない時の判定
- rulesVersion（constants.ts の主な数値の指紋）が違う → rulesMismatch
- 開始の盤面（tick 0・入力反映前）が initialHash と違う → diverged
  （seed・setup・初期キューの書き換え。開始時の熱量のように
   途中で収束して finalHash をすり抜ける細工もここで止まる。
   開始の盤面はシードと setup だけで決まるので、同じ組み立てで作り直して指紋を取る）
- 入力が受理されない / 入力が余る / 最後の盤面が違う → diverged
  （detail は「どの入力が」「どの項目がいくつ」違ったかを書く）
- finalHash は最後の盤面全体（tick を含む）の FNV-1a。endTick だけを延ばす改ざんも、
  盤面が完全に静止していても tick の値が違うので確実に検出できる。
- プレイヤーは検証後に inputs/setup を複製して持つ。作成後に呼び出し側が
  記録の配列・開始状態を書き換えても、カーソルの再計算には複製が使われる
  （record.ts が入力・setup を複製するのと同じ考え方。ハッシュ照合は作成時に
  済んでいるので、あとからの書き換えは「腐った再生」にしかならない）。
