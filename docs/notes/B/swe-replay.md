# プレイの再生（swe-replay）

## いま
- 前回の失敗（setup を後から足しても「合わない」にならない）を直した。
  原因: 開始時の熱量は途中で冷却されて最終盤面が同じになるため、finalHash 照合をすり抜けた。
- 対策: 記録に initialHash（tick 0・入力反映前の盤面の指紋）を足し、検証の最初に照合する。
  seed・setup・初期キューの書き換えを全て検出できる。REPLAY_FORMAT は 2 へ。
- 次: 長い記録でのメモリ量を測る。失敗時の detail が原因追跡に足りるかも見直す。

## 「tick T の盤面」の決め方（一番大事な約束）
`submitLaunch` は呼んだ時点の tick で盤面へ即反映される。元のプレイでは
「tick T の盤面」は T 回の stepFixed のあと・tick T の入力が撃たれる前に取られる。だから:
- 盤面 T = 「tick < T の入力」を反映して T 回進めた状態
- 入力 tick = T は盤面 T のあと、T→T+1 のステップの前に投入される
- 例外は記録の「最後」だけ: 記録直前に撃たれて 1 回も進んでいない入力（tick = endTick）が
  ありうるので、最終盤面の照合時だけ endTick の入力も反映する（再現側も同じ状態になる）

## seek の速さの設計
SimulationPort の中身は外から複製・復元できない。ある tick の状態は
「シードと入力から計算し直す」しかないので、速さを 3 段に分ける（player.ts 冒頭に詳細）:
1. キーフレーム: 検証の再計算で 60 tick ごとの盤面を覚える。捨てない。
   その tick への seek/peek は一瞬。
2. 行った所: seek で止まった盤面も覚える。上限 240 面を越えたら一番古い物から捨てる
   （Map の挿入順を利用した LRU もどき）。同じ所への再 seek は一瞬。
3. カーソル: 前にしか進めない sim を最大 4 本持ち、目的地の手前にいる物を進める。
   全部先にいる時は一番手前（最小 tick = 失う計算が最小）を捨てて 0 から作り直す。
   最悪は全計算し直し。カーソルが進めなくなる（終了した）異例に備え、
   盤面の tick は常に snapshot から取り、記憶のキーにも実際の tick を使う。
ツマミを動かしている途中の表示は peek（近いキーフレームを即返す）を使う想定。

## 記録と合わない時の判定
- rulesVersion（constants.ts の主な数値の指紋）が違う → rulesMismatch
- 開始の盤面（tick 0・入力反映前）が initialHash と違う → diverged
  （seed・setup・初期キューの書き換え。開始時の熱量のように
   途中で収束して finalHash をすり抜ける細工もここで止まる。
   開始の盤面はシードと setup だけで決まるので、同じ組み立てで作り直して指紋を取る）
- 入力が受理されない / 入力が余る / 最後の盤面が違う → diverged
- finalHash は最後の盤面全体（tick を含む）の FNV-1a。endTick だけを延ばす改ざんも、
  盤面が完全に静止していても tick の値が違うので確実に検出できる。
