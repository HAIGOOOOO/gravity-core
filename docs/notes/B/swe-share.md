## 設計の判断（覚えておくこと）
- **値は丸めない。** 物理は小さなズレが接触判定を経て増幅しうるので、「同じ計算で出せる値は計算し直す」方式にした。まっすぐ落とし（`-cos(角度)*DROP_SPEED, -sin(角度)*DROP_SPEED`）は角度だけで復元でき、自動プレイの角度は `(k/2^32)*2π` の格子に必ず乗るので u32 番号 4 バイトで済む。どの経路も誤差 0 → 再生は元プレイと完全一致する。丸める案は「再生結果が変わらない」ことを証明しにくいので捨てた。
- tick は前の入力との差 ×4 + 種別タグを varint で持つ（発射間隔 ~110 tick なら 2 バイト）。
- 検査値は FNV-1a 32bit を末尾に。**先に検査してから読む**ので、壊れた文字列の変な値を読み途中で拾わない。
- base64url は padding なし・余りビット非 0 の詰めを拒否（正規形のみ）→ 末尾側の 1 文字変化も必ず検知できる。
- 読み戻しは**正準化**になる: 大きい経路（8 バイトの角度）で書かれた格子の入力も、再び文字列にすると小さい「格子番号」形に直る。同じプレイを表す別の文字列は正規形に揃う。
- **角度 -0 は格子番号に潰せない**（6 回目に見つけた穴）: writeU32 は -0 を 0 として書くので、読み戻すと角度 +0・vy の符号が +0→-0 にずれて「ビット一致」が破れる。encode の格子判定で `Object.is(angle, -0)` を先にはじき、-0 は f64 の「角度だけ」形へ回す（それが -0 の正準形）。+0 は従来どおり格子番号 0 の小さい形。
- encodePlay も全体を try/catch で囲んだ（6 回目）。decode/verify と同じく、型を越えた引数（getter が投げる・Proxy）が来ても例外を外へ出さない。
- verify は文字列内の得点を信じない（そもそも入れない）で、createSimulation(seed) から再生して計算し直す。受理されない入力は捨てて inputsApplied で報告。ルールの版が違う物は rulesMismatch。結果の stats も全部再生した値。
- encode/decode/verify はどれも例外を外へ出さない（encode は空文字列、decode/verify は理由付きの失敗を返す）。
- **受理する形は正規形だけ**（7 回目に徹底）: base64url の余りビットに加えて、varint の最短でない形（終端 0 の多バイト列）も弾く。正規の encoder は最短形しか出さないので互換性の損失はなく、「検査値を付け直せば同じ値に化けられる別の文字列」を減らせる。
- verifyPlay は射出のたびに snap を取り直す（7 回目）。射出が phase を変えないのは今のルールのたまたまなので、ループの不変条件（「snap は常に最新」）を明示的に守る形にした。

## 上限（壊れ・DoS 対策）
- 文字列 262,144 文字まで、入力 100,000 個まで、プレイ長 4 時間（1,728,000 tick）まで。越える物は弾く。
- 実効の上限は文字列側: 全部「まっすぐ落とし（格子）」なら ~39,000 入力、全部「投げる」なら ~8,000 入力で頭打ち（それ以上は encode が空文字列を返す）。
- verify の計算量はプレイ長に比例する。悪意ある文字列（endTick 最大・入力なし）で最悪 1,728,000 tick を再生する。**対策済み（6 回目）**: `verifyPlay(text, { maxTicks })` で再生 tick 数を打ち切れる。越えると 'tooLongToVerify' で失敗し、最悪ケースでも maxTicks 回の step で止まる。既定は上限なし（正当なプレイは必ず最後まで確かめる）。ゲームが先に終わる文字列は上限を越える endTick でも終了時点で止まり成功する。UI 統合時は maxTicks を渡すかワーカー化を検討（リーダー・統合案件）。

## 測った物・測り方
- 文字列長の理論見積もり: 3 分自動プレイ ≈ 約 197 入力 × 6 バイト ≈ 1.2 KB → base64 で約 1.6K 文字。テストで ≤ 2,000 文字を assert 済み（実測値は検査ログの `[share]` 行に出る）。
- 速さ: verify.test.ts の「3 分のプレイ」が encode/decode/verify を、tamper.test.ts の「上限近く」が 30,000 入力（約 20 万文字）の encode/decode を performance.now() で計測し console.info に出す。上限は緩い足切り（それぞれ 90 秒・30 秒）。
- 細工耐性: tamper.test.ts で「検査値を付け直した文字列」（未知タグ・tick 越え・個数不整合・NaN 混入・正準化）を手組みして弾くことを確認。
- 再生上限（6 回目）: verify.test.ts に maxTicks のテスト。入力なし・endTick 最大の文字列を 3,600 tick で打ち切る、上限ちょうどなら上限なしと同じ結果、1 つ足りない上限と入力途中の上限で弾く、0・負・NaN・文字列などの不正値は「上限なし」として例外なく動く、を確かめる。
- 正規形の徹底（7 回目）: coding.test.ts で冗長 varint の単体拒否、tamper.test.ts で検査値を付け直した細工（個数・入力の頭の冗長形、endTick 上限超過、seed 2^32）を弾くことを確認。
- 極値の往復（7 回目）: codec.test.ts で非正規数（5e-324）・±0・MAX_VALUE を含む「投げる」入力のビット一致往復を乱数 120 ケースで確かめる。生の値の経路は f64 ビットをそのまま持つので欠けは無いはず、の裏付け。
- endTick の境目（7 回目）: verify.test.ts で「最後の入力の tick = endTick」「入力なし・endTick 0」「decode の失敗理由のそのまま伝播」を確かめる。

## 確かめていない事
- 実機ブラウザでの実行（テストは node 環境。使っている API は Uint8Array/DataView/Math だけなので環境差は出にくいはず）。
- JS エンジン間で Math.cos/sin/hypot の最下位ビット一致は仕様上は保証されない（シミュレーション全体の前提で、codec の問題ではない）。異なるブラウザどうしの共有で理論上は結果がずれうる。実装は各社 fdlibm 系で一致するはずだが未検証。
- setup ありで始まったプレイ（通常プレイ以外）は共有の対象外 — 文字列に初期盤面は入らないので verify は標準開始盤面で再生する。通常プレイ以外を共有したいなら仕様の拡張が必要（リーダー案件）。
- オーバーで終わったプレイの共有はコードパス上は扱えるが、テストで「実際にオーバーになったプレイ」を作るのは長いので、endTick 超過テストで間接的にカバー（オーバー/非オーバー両分岐で検証）。
