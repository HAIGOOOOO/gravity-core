2026-11-24、方針の版11。main `3fc60de` を取り込み、11/24 10:50の★★指摘を優先した。PR #13は取り込み済みで、本体終了への接続はリーダーの `18e6c94`。記録11の合否とは別に扱う。時計巻戻りとtransaction無応答はこの周では直していない。

## 調べた実物3件と3案

11/24に公式資料を確認した。

- [WHATWG Storage](https://storage.spec.whatwg.org/#storage-endpoints)：localStorageの推奨枠は5MiB。再生で全部使う前提にせず、最高点と設定に空きを残す。
- [W3C Web Locks](https://www.w3.org/TR/web-locks/)：同じoriginの別ページで、共有する保存口の予算確認と追記を順番に行える。待機を永続化せず3秒で未保存として返す。
- [WebKit Safari 15.4](https://webkit.org/blog/12445/new-webkit-features-in-safari-15-4/)：Web Locks導入が記録されている。Safari実機で試したという意味ではなく、未対応・拒否時の道も分ける。

比較した案は次の3つ。

1. 書いた後でだけ容量を減らす。上限まで書く段階で拒否され、最高点の空きも無くなるため採らない。
2. journalを1個の共有JSONへまとめ直す。同時の別ページの上書きで1件を失うため採らない（4周目の実測済み）。
3. **UUID別の追記を維持し、履歴を先に確保してから再生へ予算を割り当てる。** 共有予算は別ページと順番に確認し、上限を超える場合は古い再生から外す。得点と詳しい統計を残せるため選んだ。

## 変更と限界

- journalの合計をキー込み100万文字までにする。UTF-16換算で約2MB。DB正常時にlocalStorageへ写しを書かない4周目の動作は維持する。
- 再生を全て外しても入らない場合、履歴を削って成功扱いにはせず、ページ内の未保存として返す。壊れた原文も予算に数えるが消さない。別機能や既存の壊れた原文が既に保存口を使い切っている場合まで保存成功は保証しない。
- `replayOmitted: capacity` は容量による除去、`unavailable` は再生の追加書込が拒否された状態。いずれも得点と詳しい記録が端末へ残った場合だけ`persisted: true`。表示と読み戻しでも理由を保持する。
- Web Locksが使える場合は別ページも同じ名前で順番に保存。3秒の待機超過や拒否は原本へ書かず未保存として返す。**DBが開けずWeb Locksも無いブラウザは、ページ内の保持だけに制限する。** タブ間の古い読取値では容量を予約できず、未対応時に同時600k再生を保存すると10回とも合計1202068文字になったため。DB正常時はWeb Locksなしでも保存できる。
- 履歴だけの小さい値を先に確保するため、整理途中に一時的にその1件分だけ100万文字を超える場合がある。再生全体を先に書くことはせず、完了後の合計を再確認する。

## 独立審査で直した★

最初の候補は、新規キーを拒否された保存で`persisted: false`なのに、既存再生600299文字が0になった。新規書込前に古い再生を縮めていたため。履歴の新規キーを先に確保し、その書込が拒否された時は既存原文を一切変えないよう修正した。再生の追加だけが拒否された場合は履歴と理由を残す回帰試験も加えた。

次の境界では再生の追加だけ拒否され、履歴は残るが既存再生まで縮んでいた。再生追加失敗時は、rawが一致し予算内に戻せる既存再生を復元するよう修正。独立再検査で旧600299文字の再生を保持し、新しい履歴は`unavailable`として読み戻せた。

さらに担当B本人の最終照合で、Aを一度保存拒否→次のB保存成功で未保存Aを保存済み扱いにして消す既存の欠点を回帰試験で再現した。次の成功時には未保存全件をjournalへ書き、全部成功した後だけ未保存状態を片づけるよう修正した。最後の独立ブラウザ確認でも、第三ページのA/B保持、新規拒否時の旧原文保持、再生追加拒否時の旧再生保持を各1回再確認した。

最終の独立再審査では、通常10回と容量近傍10回の2ページ同時保存で全40件が保存成功、全回両ID保持、最大601734文字。DB復旧でA/B/Cを統合し確定後だけjournalを削除。壊れた原文も保持した。Web Locksなしのfallback10回は端末へ書かず未保存とし、同じstoreのメモリ保持を確認した。

時計巻戻りは、1000件・592022文字で新しい1件が`tooLarge`になることを審査役も再現。実DBのtransaction占有中も4100ms後にaddが返らず、占有を解いた後に返る。既存の★残件として次へ引き継ぎ、この周で直ったとは書かない。

## 検査と測定

1000履歴・100再生、3回空回し後5回の新store作成・ready・loadを測定した。DBは40.5・35.1・39.1・37.4・32.7ms、中央値37.4ms。journalは38.9・36.8・39.2・32.0・30.7ms、中央値36.8ms。全回1000件・再生100件、基準50ms以内。再生を増量した容量検査とは別の、同じ30秒の自動見本を元にした計測用データ。

容量の回帰試験は、UTF-16換算5MiBの模擬保存口に別機能150万文字を置き、約40万文字に増量した形の正しい再生を6回保存する。各回でjournal上限と、その後の最高点・設定の保存/再読込を確認した。人が長時間遊んだ6件とは扱わない。

Edge390×844でも自動見本6件を増量したデータで検査。6件すべて保存、journalの物理キー込み805894文字、古い4件の再生だけ除去、最高点987654・音量33を保存/再読込。ページ再読込後、新しい通常の30秒見本を保存して履歴7件、除去理由4件、再生終端11,850点。文書幅390px、例外0。[検査画面](capacity-mobile.png)は[CREDITS.md](CREDITS.md)を参照。

審査で比較した実在の物は[Chess.comの対局履歴](https://support.chess.com/en/articles/8598090-how-do-i-view-my-own-games)。自分の履歴の参照と、選んだ対局のPGN取得ができる。今回の部品には、端末の保存が使えない場合に記録を取り出して別に保管する導線と、復旧の再試行操作が足りない。次の改善候補とし、人による見た目の合否とは扱わない。

最後の未保存再試行修正を含む対象43件と型が通過。最終の全746件（63ファイル）、本番build（内部の型検査を含む）・見本build・ownershipも通過。途中の741件・745件の結果だけで提出したものではない。依存や設定の追加は無い。
