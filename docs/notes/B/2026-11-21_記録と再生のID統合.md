# 記録11の準備：履歴と同じプレイを開く

2026-11-21、方針の版11。発表の方向選定待ちに調査。実装は発表の作り直しの後。ここは設計メモで、11を直した報告ではない。

## 実物3件

- [Trackmania公式の再生案内](https://doc.trackmania.com/play/watch-replays/)：順位表の記録から、そのプレイのゴーストを読み込める。持ち帰るのは、結果から同じプレイへ進む関係で、別ゲームの保存形式をそのまま採用する意味ではない。
- [Strava公式API](https://developers.strava.com/docs/reference/#api-Activities-getActivityById)：活動IDを指定して同じ活動の詳細を取得する。得点・日時の近さで関連付けず、識別子を使う参考。
- [Chess.com公式の公開API](https://www.chess.com/news/view/published-data-api)：月の対局データに個々の対局URLと棋譜を含め、まとめたPGNの出力もある。一覧・詳細・持ち出す形式を同じ元データに基づける参考。

以上は11/21に公式ページを再確認した内容。下は本プロジェクトへの設計上の推論。

## 現状

- `RunRecord.id` と `RunDetail.id` はあるが、`ReplayRecord` は別形式でIDが無い。
- 詳細は `gravity-core:stats:v1`、見本の再生は `gravity-core.replay-demo.v1` の1件保存。本体は終了時の再生をメモリで持つ。
- 共有文字列には元端末のIDを運ばない。受信時の再計算から再生を作り直すので、共有往復で元端末のIDが戻ると扱ってはいけない。
- 特別な開始配置の再生や古いルールは共有できない。空文字の共有を正常なURLへ変えてはいけない。

## 3案

1. 既存3形式にそれぞれIDを足し、別々に保存する。移行は小さいが、保存に一部だけ成功した時に別プレイや欠落を生みやすい。
2. 同じIDの1件に、履歴・詳しい統計・再生をまとめる。共有はその再生から作り、共有文字列を重複保存しない。新規終了は3点を一緒に検査して保存する。これを次の実装の第一候補にする。
3. 入力ログだけを保存し、履歴・統計を開くたびに再計算する。1件の元は明快だが、1000件の一覧が重くなり、出来事が無い旧記録の不明項目も復元できない。

## 実装前に決める境界

- 本体の終了処理が作った `RunRecord.id` を渡す。得点・seed・終了時点が違う3点は同じ1件として受け付けない。
- 過去の履歴には再生が無くてもよい。詳細のnullを0へ変えず、情報が無い物は欠落を明示する。
- 統計1000件と本体の再生最新100件の合意を両立する。100件を超えた再生は消しても、得点・詳細の履歴は消さない。総バイト上限、保存拒否とメモリ継続も試験する。
- 共有を受け取って端末へ残す場合は、端末内の新しいIDと、元の盤面の指紋を区別する。同じ入力なら同じ人の同じ1回だという推測で結び付けない。
- 旧保存はバックアップを残し、同じIDの置換・壊れた入力・古いルール・容量超過・共有往復を回帰試験する。既存の保存を自動で全部捨てない。
- `src/app/` はリーダーの場所。Bの統合入口と見本で動作を示してから、終了時の接続とtickごとの統計の収集を依頼する。

調べ役へ型と呼出元の読み取りだけを依頼し、上の設計判断は担当Bの本体が行った。実装・新しい試験・本体接続はまだ。

## 11/22の実装後

2案目の共通保存を実装した。`RunBundle`は `RunRecord`・`StoredRunDetail`・`ReplayRecord` と終了時点の `GameSnapshot`。最後の盤面も渡すのは、再生の形式だけでは読めない到達天体を照合するため。共有はその再生から作る。

複数タブの審査で、localStorageはWeb Locksの後でも直前の書込を読めない回があった。IndexedDBのreadwrite transactionを正に変更し、localStorageは互換の写しとした。古いキーとbackupを消さず、見本は通常の履歴とは別の領域へ保存する。結果は [3周目の確認](records-cycle3/checks.md)。本体接続は11/21 06:15の返事どおりリーダーが行う。
