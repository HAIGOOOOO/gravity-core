# 題目1 再生の作り直し（方針9）

## 実物の調査

2026-10-23に公式ページを取得して読んだ。画面を借用した物や素材の追加はない。

- [Factorio / Deterministic save/load](https://www.factorio.com/blog/post/fff-270)（Wube、2018-11-23）: 途中保存と読み戻しの前後で観測できる結果が変わらないことを求めている。絵だけを途中保存しても続きの乱数・待ち時間・イベントを再現できない。GRAVITY COREではリーダーの `exportState` / `restoreSimulation` を使い、入力位置と一緒にメモリへ保存する。数値の丸め直しや独自の物理は作らない。
- [Unity Timeline / Playback Controls](https://docs.unity.cn/Packages/com.unity.timeline@1.8/manual/tl-play-ctrls.html)（Unity、Timeline 1.8）: 時間の目盛りと再生位置を一緒に扱い、いまの位置から再生・停止できる。記録を選ぶ操作と、記録の中を移動する操作を分ける根拠にする。
- [QuickTime Player / Keyboard shortcuts](https://support.apple.com/en-sg/guide/quicktime-player/qtpa4808515d/mac)（Apple、閲覧2026-10-23）: 再生・停止、前後の移動、速度変更が同じ映像に作用する。GRAVITY COREでも速度だけを変えた時に位置を変えず、先頭に戻る時は明示操作にする。

## 1周目の3案と選択

1. 毎tickの盤面を全部保存する: 飛ぶのは速いが、10分で72,000面を抱える。
2. 計算状態を一定間隔で保存し、近い所から続きを計算する: 正しい巻き戻しと保持量の上限を両立できる。
3. 別スレッドで毎回先頭から計算する: 応答は止まりにくいが、飛ぶたびに長い待ちが残る。

2を選ぶ。見本のつまみでどこを指しても、その場所の正確な盤面が短時間で出ることを優先した。読み込みの非同期化は別の問題として残す。

## 測定の条件

- Windows / Node 22.23.3。`npm ci`でロックファイルどおりに導入。依存関係の追加・更新はしていない。
- 10分の測定は最初の30秒を既存自動プレイで投入し、残りも本物の物理を進めた記録（受理33投）。10分間ずっと人が投げ続けた記録の測定ではない。
- 初回: 検証・保存点生成2,276.7ms、未訪問の前後40地点への最大seek3.61ms、保持概算5,189,063バイト（メモリ。端末保存のサイズとは別）。
- 既存の通常テストは変更前640/641。1000件の記録読み込みが166.6msで50ms基準に届かなかった。再生の修正と分けて追跡する。
- 実機のスマートフォン、人間が10分操作した記録、低速端末は未検証。
