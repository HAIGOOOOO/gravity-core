# 記録11・4周目：開けない保存先と容量

2026-11-24、方針の版11。main `bf80820` の本体接続前の突き返し1〜3を直す。PR #11の取り込みは合格と扱わない。`src/app`は変更しない。

## 調べた実物3件と選択

- [Indexed Database API](https://www.w3.org/TR/IndexedDB/#transaction-scheduling)：同じ対象へのreadwrite transactionで、最新の読込と更新をまとめる。transactionの失敗はopen失敗と分ける。
- [WHATWG Storage](https://storage.spec.whatwg.org/#storage-endpoints)：localStorageには5MiBの推奨枠がある。最高点・設定と同じ保存口へ再生を二重に置かない。
- [WebKitの保存方針](https://webkit.org/blog/14403/updates-to-storage-policy/)：上限いっぱいまで必ず書ける保証はなく、QuotaExceededErrorを処理する必要がある。空き容量がある前提で保存成功としない。

11/24に公式の説明を確認。次の3案を比較した。

1. どのDBエラーでもlocalStorageへ書く。開けたDBのtransaction失敗まで別保存へ切り替えると、正と未保存分の区別が崩れるため採らない。
2. **openだけを3秒で区切り、その失敗時だけlocalStorageへ切り替える。** 通常のDB経路では写しを書かない。この案を選ぶ。使える保存口を残し、最高点・設定用の容量も奪わない。
3. DB失敗時は常にページ内の保持だけにする。破壊は避けられるが、localStorageだけ使える端末で保存できないので採らない。

## 変更

- openのエラー・blocked・同期例外・3秒の無応答を専用の失敗として扱う。遅れて成功した接続は閉じ、時間切れ後のupgradeは中断する。
- open失敗時だけlocalStorageへ移る。開けたDBのtransaction失敗は、正と追記原文を変えずページ内に保持する。書けない状態は`unsaved`とし、読めない状態と分けて表示する。
- DB成功中はlocalStorageの大きな写しを書かない。旧キーとbackupは保持する。
- 表示のたびに`await store.ready()`を待つ手順を明記。時計を戻した時の再生保持（突き返し4）は、リーダーが次周可とした残りとして扱う。

## 審査で追加修正した★2件

単にlocalStorageの共有JSONへ切り替えると、別の2ページが上書きし合い、20回すべてで1件を失った。また、DB復旧後に切替先の1件が見えなくなった。

切替先ではUUIDごとの追記へ保存する。表示時に統合し、DB復旧後の次の保存では同じtransactionで統合する。DBへの確定後だけ取り込んだ追記を片づける。古い主キーやbackup、読めない追記の原文は消さない。

- 新しいBrowserContextで2ページから同時保存を20回。全40件が保存成功、各回で2IDと2件の追記原文を保持。
- DBでA保存→open失敗でB保存→DB復旧でA/Bを表示。この段階ではBの追記を保持。次のC保存後にDBと新規ページのA/B/Cを確認してから追記を削除。
- 移行中のput失敗ではDB原本と追記を保持。次のD保存で未保存分も統合。
- 無応答のreadyはEdgeの注入試験で約3001.8msで返り、その後の切替保存は約2.1ms。

独立した審査役は、この条件で★2件を再現しなかった。見た目の合格とは扱わない。Safari実機で試したという意味ではない。

## 性能と残り

最初の候補は1000履歴・100再生の読込中央値97.4msとなり、基準50msを超えた。検査済みのlocal保存をキャッシュし、同じrawのDBを二重検査せず、検査済み再生を毎回再圧縮しない形へ変更した。3回空回し後の5回は37.8・36.6・41.2・35.7・39.5ms、中央値37.8ms。毎回新storeの作成・ready・loadを含む。

UTF-16換算5MiBの保存口を模した回帰試験で、DB保存の後でも最高点と音量設定を保存・再読込できることを確認した。対象38件、通常全体735件（62ファイル）、型・本番build・見本build・ownershipが通過。
